## Load and interpretation methodology

1. Inspect relation sizes/statistics before exact scans. Structured heaps <5 MB at this audit;
   count/null/date probes are inexpensive bounded aggregates. Raw payload storage ~394 MiB;
   avoid full PDF decoding/export and all-history JSON casts.
2. SQL executes serially within each probe set; independent metadata/code inspection was parallelised.
3. Counts are labelled exact/estimated: P01 exact; S04 statistics estimated/stale. Distinct raw hashes are
   content repeats, not duplicate business records. Current facts require `superseded_at IS NULL`.
4. Compare at matching grain: raw department-day sums versus daily facts, product-day keys, invoice line sums
   versus purchasing projection, chosen source versus resolved daily value. Never assert pages==canonical rows.
5. Count missing fields against the relevant population. No expected source population was available;
   date presence ≠ source completeness. Absent purchase-day can be zero activity or an unknown gap.
6. Invoice repeat/tail/price-difference counts are diagnostic candidates. No deletion/repair conclusion follows
   without identity/window/unit/control evidence.
7. Separate current snapshot correctness from source truth. Query sets use read-only transactions at normal
   read-committed isolation, **not a single consistent snapshot of the entire audit**. Concurrent scheduled/operator
   activity can change counts between evidence captures. No source data changes were attributed to the auditor.
8. Exact original build commit remains release metadata unless reproducible image/source attestation exists.
   Copied JAR reports Spring Boot 3.5.0, app 0.1.0-SNAPSHOT, JDK 25 manifest; its two application YAMLs exactly
   match checkout hashes. Data backend Git sources have no diff between release metadata c3377bb and f6140b8.
9. Do not claim UI pixels from DTO/source analysis: authenticated runtime was inaccessible without a write/login.

## Additional safe SQL for business checks

### Query current supplier spend at correct ex-tax line grain

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout='5s';
SELECT count(*) AS suppliers,sum(spend) AS purchase_control
FROM (
 SELECT i.supplier_name,sum(l.line_total) AS spend
 FROM public.canonical_invoice_line l
 JOIN public.canonical_invoice i ON i.invoice_number=l.invoice_number
 WHERE l.superseded_at IS NULL AND i.superseded_at IS NULL
   AND l.invoice_date BETWEEN DATE '2026-10-01' AND DATE '2026-10-08'
 GROUP BY i.supplier_name
) s;
ROLLBACK;
```

Identity collisions remain a qualifier; avoid adding header totals once per line.
For record detail an authorised operator can SELECT explicit fields with date/limit and **keep private results local**.

### Historical observation and invoice control

```sql
SELECT count(*) FROM public.canonical_invoice_line
WHERE recorded_at <= timestamptz '2026-10-08 12:00:00+00'
AND (superseded_at IS NULL OR superseded_at > timestamptz '2026-10-08 12:00:00+00');

WITH lines AS (
 SELECT invoice_number,sum(line_total) AS line_ex_tax
 FROM public.canonical_invoice_line WHERE superseded_at IS NULL GROUP BY invoice_number
)
SELECT count(*) AS mismatched_headers
FROM public.canonical_invoice i JOIN lines l USING(invoice_number)
WHERE i.superseded_at IS NULL AND abs(i.amount_ex_tax-l.line_ex_tax)>0.01;
```

Run these inside the same read-only/timeout wrapper. Valid-time alone is not a correct as-of selector.
