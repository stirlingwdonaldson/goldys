# Transaction export and evidence schema

## Proven manual access path

Use an authenticated Lightspeed Back Office session with access to Reports > Sales Feed. Select Sales Filter: Goldy's Tavern (site 96181), All Registers, All Payments, empty customer filter, Hide deleted options checked, start date 26/10/2026, end date 01/11/2026; apply, allow the grid to finish loading, then use the cloud download control. Export is CSV. The grid calls the displayed timestamp Date/Time; CSV calls it SaleDate. The applied UI parameters recorded 00 for the first hour and 23 for the last hour. UI date selection was inclusive by calendar day in the sample, and seven adjacent daily exports exactly equal the combined export. Exact second-level boundary and source timezone rules are not established. Values carry no offset; do not interpret them as UTC or claim a guaranteed timezone. Insights comparisons used Australia/Sydney. The site was explicitly selected by numeric ID, while CSV carries SiteName rather than that numeric ID: retain the selection as export-level metadata.

Authentication is a signed-in Back Office session; no credential or session material is included. No programmatic transaction connector or sustained automated retrieval has been proven. The page reported 5,411 items; each combined CSV has 5,415 distinct nonblank SaleIDs. No export limit was offered by the UI, and no source-side maximum or historical completeness is established. Use a real CSV parser: the source is valid UTF-8 without BOM, CRLF record separators, quoted CSV fields and embedded newlines; 1,954 of 5,415 records have an embedded newline in at least one original field. Source rows in this sample have no totals row, blank or duplicate SaleID.

## Exact source headers

Original Sales Feed CSV header, in order:
`SaleID, SaleNo, SaleDate, SiteName, TerminalName, CustomerName, Operator, Notes, LinkedSaleID, Net Amount, Tax Amount, Tip, Total`.

Minimized transaction files preserve exactly these original headers and values: `SaleID, SaleNo, SaleDate, SiteName, LinkedSaleID, Net Amount, Tax Amount, Tip, Total`. `TerminalName, CustomerName, Operator, Notes` are deliberately removed. SaleID is an observed transaction identifier; SaleNo is the displayed receipt number, not a verified unique transaction key. LinkedSaleID explicitly references another transaction ID when populated; it can point outside an import window in principle, but all eight linked rows in this sample resolve inside the seven-day export. Negative totals and explicit links appear on four records; no transaction-type or status column is supplied. Zero-total transactions occur; zero does not mean no payment. Total includes tip in the source's documented semantics, and tips in this sample are all zero. Values, signs, and empty fields were preserved as strings; no inferred type, status, date, or identity is added.

Mapping headers: `Sales Data Receipt Line ID, Saleline Payments Sale Number, Site Numeric ID, Sales Data Sale Closed Date`; source fields respectively `salelines.id, saleline_payments.sale_number, site.numeric_id, salelines.sale_date`. This is an observation mapping, not an amount source. Identical observations can repeat.

Financial headers: `Sales Data Receipt Line ID, Sales Data Sale Closed Date, Site Numeric ID, Sales Data Sale Type, Sales Adjustments Adjustment Type, Sales Data Product Quantity, Sales Data Total Ex Tax, Sales Data Total Tax, Sales Data Total Inc Tax`. These are a field-selected derivative of the full no-payment financial export. The source sale type is not a transaction-export field. The original contains other fields including staff and customer information which were dropped.

`example-transactions.csv` selects one ordinary transaction, the known split-payment receipt, the same-number sale/refund pair, and the different-number linked pair. `example-split-payment-observations.csv` contains two original export observations for the same line and their tender types. These are evidence of duplication, not financial facts to sum or an authorized line-to-SaleID join.

## Proposed import semantics, not established source behavior

Retain each CSV as immutable source evidence, with import time, site selection, selected date window, checksum, and capture scope. Upsert/version transaction observations by the real SaleID within a verified source/company scope; retain SaleNo and LinkedSaleID as observed fields and allow unresolved targets. Keep mapping observations and financial lines separate. Flag a site/number with multiple observed SaleIDs and use the link graph when known; neither establishes a line-to-SaleID assignment. Re-import overlapping periods and resolve previously absent link targets as later evidence arrives; do not treat absence in one export as a deletion or prove completeness from reconciliation. Reopen/late-payment behavior, site-key scope, source version ordering, stable refresh interval, and downstream security/ingestion controls still need implementation verification.
